# money-tracker.online — Localisation contract

Two locales: **`en` (source)** and **`pl`**. Both LTR. There is no third locale in v1, and adding one
is a plan with a stage, not a pull request. `docs/SPEC.md` §9 is the address other documents cite;
this document is the detail.

---

## 1. Why we do not use an i18n library

The catalogue, the negotiator, the plural machinery and the provider are ours, about 400 lines in
total, under `src/lib/i18n/`. That is a deliberate trade and it is worth stating:

- Two locales, both LTR, both with well-understood plural rules. The general case a library solves
  is not the case we have.
- Our messages carry **money and dates**, which must be formatted through
  `@internationalized/number` and `@internationalized/date` with the workspace's currency and the
  reader's locale. A library that concatenates pre-formatted strings is the thing we are avoiding.
- The catalogue is loaded through `import.meta.glob`, so a locale is a code-split chunk and an
  unused locale never reaches the client.
- The **parity test** (§4) is the completeness gate, and it is easier to write against our own shape
  than against a library's.

The cost is that we own the plural implementation, which is why §3 is as specific as it is.

## 2. The catalogue

```
src/lib/i18n/
  locales.ts        the frozen locale table
  negotiate.ts      user → workspace → Accept-Language → 'en'
  catalogue.ts      import.meta.glob over messages/
  provider.tsx      React context (RAC's I18nProvider is mounted by the layouts, see §5)
  plural.ts         CLDR plural category selection
  format.ts         number, currency, date and relative-time formatters
  messages/
    en/  common.json  auth.json  accounts.json  transactions.json  budgets.json …
    pl/  common.json  auth.json  accounts.json  transactions.json  budgets.json …
```

### 2.1 Keys

Dotted, lowercase, namespaced by the file: `transactions.list.empty.title`. The namespace is the
file name, so a key's file is derivable from the key and a reviewer can find it without grepping.

- **A key names its meaning, not its text.** `transactions.form.amount.label`, never
  `transactions.form.enterAmount`.
- **A key is never built at runtime.** `t(\`status.${s}\`)` defeats the parity test and the
  unused-key sweep. Use an exhaustive record from the union to a literal key.
- **A new key lands in both `en/` and `pl/` in the same change.** The parity test fails otherwise,
  and a `pl` value that is a copy of the English string is a failure too (§4).

### 2.2 Interpolation

```json
{ "budgets.alert.crossed": "{name} has used {percent} of its limit" }
```

Parameters are named, never positional. Values that are numbers, amounts or dates are passed as
**values**, not as pre-formatted strings, and the formatter resolves them against the active locale
inside the message. Concatenating `formatMoney(x) + " " + t('...')` at a call site is a defect: it
produces "12,50 zł spent" in a language whose sentence order puts the verb first.

### 2.3 What is never translated

- Currency **codes** (`PLN`, `EUR`). Their expanded names are, in the currency picker only.
- Account names, category names, tag names, payee names and notes — user content.
- The rules of arithmetic. A Polish reader sees `1 234,56 zł` and an English reader sees
  `PLN 1,234.56`, and both are the same integer `123456` minor units.

## 3. Polish plurals: four categories, and why an `if` is a defect

CLDR gives Polish four plural categories, and all four are reachable with ordinary transaction
counts:

| Category | Rule (integers)                        | Example counts | Polish         |
| -------- | -------------------------------------- | -------------- | -------------- |
| `one`    | n = 1                                  | 1              | 1 transakcja   |
| `few`    | n mod 10 = 2..4 and n mod 100 ≠ 12..14 | 2, 3, 4, 22    | 2 transakcje   |
| `many`   | everything else integral               | 0, 5..21, 25   | 5 transakcji   |
| `other`  | fractions                              | 1.5, 0.5       | 1,5 transakcji |

```json
{
  "transactions.count": {
    "one": "{count} transakcja",
    "few": "{count} transakcje",
    "many": "{count} transakcji",
    "other": "{count} transakcji"
  }
}
```

English uses `one` and `other`. A message with a count **always** uses the plural form, even when
English needs only two branches — otherwise the Polish catalogue has nowhere to put `few`.

`if (n === 1)` in a component is a defect. So is `n + ' ' + t('transactions')`. Both are correct in
English and wrong in Polish for most values, which is exactly the kind of bug that ships.

Category selection goes through `Intl.PluralRules` for the active locale; we do not hand-roll the
rule table.

### 3.1 Genitive and case

Polish inflects. A message that embeds a noun supplied at runtime — "Delete {entity}?" — produces
the wrong case roughly half the time. The rule: **no message interpolates a translated noun into a
sentence.** Write a separate key per entity (`accounts.delete.confirm`, `budgets.delete.confirm`),
even though English would have made one generic key do. The duplication is small and the alternative
is a product that reads as broken Polish.

User-supplied names are safe to interpolate — they are quoted and are not inflected.

## 4. The parity test

`src/lib/i18n/__tests__/parity.test.ts` is the completeness gate. It fails when:

1. A key exists in `en` and not in `pl`, or the reverse.
2. A key's **parameter set** differs between locales — `{name}` in one and `{title}` in the other is
   a runtime hole, and it is caught here rather than by a reader seeing `{title}`.
3. A key's **plural categories** are missing for the locale: `pl` must supply `one`, `few`, `many`
   and `other` for any key `en` marks as plural.
4. A `pl` value is **byte-identical to its `en` value** and is not on the short allow-list of things
   that legitimately do not translate (`OK`, `PIN`, `CSV`, `OFX`, `QIF`, brand names, currency codes).
   An untranslated string that silently ships as English is the single most common i18n failure and
   it is the one an eyeball review never catches.
5. A key exists in a catalogue and is referenced nowhere in `src/` (the unused-key sweep). Dead keys
   accumulate and make the parity signal noisy.

## 5. Negotiation

Order, evaluated per request:

1. `user_preferences.locale`, if set.
2. `organization_settings.locale`.
3. The `Accept-Language` header, negotiated against the frozen table.
4. `'en'`.

Every input is **normalised against the frozen table, never trusted**: a value that is not
`'en'` or `'pl'` after normalisation resolves to `'en'`. `pl-PL` normalises to `pl`; `en-GB` and
`en-US` normalise to `en`.

The resolved locale is put on the document (`<html lang>`), into RAC's `I18nProvider`, and into
`Intl` formatter construction. Those three must never disagree — a page whose `lang` says `pl` while
its number formatter says `en` produces `1,234.56` announced by a Polish screen reader.

RAC's `I18nProvider` is mounted by `AriaI18nProvider` (`src/components/app/shell/aria-i18n.tsx`)
inside the two layouts that render React Aria primitives - the guarded shell and the auth frame -
not by the document shell in `__root.tsx`. The root renders the marketing page too, and a
`react-aria-components` import there would ship the library to a page that uses none of it.

### 5.1 The auth screens are a special case

The authentication screens have **no stored preference to read**: the person is not signed in.
Locale there comes from `Accept-Language` alone.

Zod bakes its messages at schema-construction time, so an auth form schema built at module scope
would freeze whichever locale loaded first. Auth schemas are therefore built by a **factory** taking
`{ t, locale }` and constructed per render. This is not a style choice; it is the reason the login
form's validation messages are not permanently English.

## 6. Formatting

One module, `src/lib/i18n/format.ts`, wrapping `@internationalized/number` and
`@internationalized/date`. A second `Intl.NumberFormat` constructed anywhere else is a defect
(`docs/SPEC.md` §8, one concept one owner).

| Kind          | Rule                                                                                                                               |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Money         | `currency` style, `minimumFractionDigits = maximumFractionDigits = currencies.digits`. Never abbreviated outside a chart axis tick |
| Plain number  | Locale grouping. `pl` uses a narrow no-break space as the group separator and `,` as the decimal                                   |
| Percentage    | One decimal place, locale-formatted                                                                                                |
| Calendar date | `@internationalized/date` with the workspace calendar. Never `toLocaleDateString` on a bare string                                 |
| Instant       | Formatted in the **reader's** timezone; calendar dates are never given a timezone                                                  |
| Relative time | `Intl.RelativeTimeFormat`, and never below one-minute granularity                                                                  |
| List          | `Intl.ListFormat` — Polish conjunction is not `", "` + `" and "`                                                                   |

Formatter instances are memoised per `(locale, currency, options)`; constructing an
`Intl.NumberFormat` inside a virtualised list row is a measurable cost at 60fps.

### 6.1 Money formatting is locale-and-currency, not locale-or-currency

The **locale** decides separators and symbol placement. The **currency** decides how many decimal
places exist. They are independent inputs and both are always passed. A Polish reader looking at a
JPY account sees `1 234 ¥` with no decimal part; an English reader looking at the same account sees
`¥1,234`. Both are the integer `1234`.

## 7. Server-side i18n

Two surfaces produce localised text on the server, and neither may store a rendered sentence:

- **Notifications.** Rows store `title_key`, `title_params`, `body_key`, `body_params`. The sentence
  is rendered at read time in the reader's current locale. A person who switches language sees their
  whole notification history in the new language, which is the correct behaviour and is only
  possible because nothing was rendered at write time.
- **Emails.** The envelope carries the key set and the recipient's locale, resolved at send time from
  the recipient's own preference — not from the actor's. React Email templates are imported
  **dynamically**, so a ~540 kB dependency never lands in a cold start for a request that sends no
  mail.

The same rule covers audit-log entries and import row errors: they store a code and parameters, not
a message.

## 8. Copy rules

- **English is the source.** Polish is authored **from our own English**, never carried across from
  any other product, in any language. The clean-room rule of `docs/SPEC.md` §1 binds translations
  exactly as it binds code.
- **A language is named in its own language**, from the frozen table: _English_, _Polski_.
  `Intl.DisplayNames` is never used for this — it resolves in the _reader's_ locale, so a Polish
  reader would see "angielski" where the switcher must say "English".
- **Polish uses formal address** (`Państwo` / impersonal constructions), not `Ty`. Financial software
  addressing a person informally reads as unserious in Polish, which is the opposite of what this
  product needs.
- **No accessibility claim may be translated more strongly than `docs/ACCESSIBILITY.md` §1.** A
  translation is a representation too.
- **Marketing copy carries no fabricated evidence in any locale** — `PRODUCT.md` → Evidence on Hand
  applies to the Polish site identically.

## 9. Testing localisation

- **Parity** (§4) runs in `pnpm test` and gates every change.
- **Visual**: the e2e suite renders every route in the visual spec in **both locales**. Polish
  strings are systematically longer than English — `Powtarzające się płatności` against
  `Recurring` — and a layout that only ever saw English breaks on the first Polish page. This catches
  it before a reader does.
- **Formatting**: unit tests assert `pl` groups with a narrow no-break space and decimalises with a
  comma, that a JPY amount renders with no decimal part in both locales, and that a KWD amount
  renders with three.
- **Plural**: unit tests assert all four Polish categories for counts `1, 2, 5, 12, 22, 25, 1.5`.
