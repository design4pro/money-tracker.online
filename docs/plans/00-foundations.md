# 00 — Foundations

## Area brief

This plan owns the **eight shared paths** and nothing else. It ships no feature and closes no
product row of its own. Its stages exist so that the files every other plan needs to touch have
exactly one writer at a time.

| Shared path               | What foundations guarantees about it                                    |
| ------------------------- | ----------------------------------------------------------------------- |
| `src/server/db/schema.ts` | One module, one migration per stage, additive only                      |
| `src/server/worker.ts`    | Every DO class, the queue consumer and the cron handler are exported    |
| `wrangler.jsonc`          | Bindings, migrations, queue limits and cron triggers, both environments |
| `src/styles/tokens.css`   | The complete token contract of `DESIGN.md`, light and dark              |
| `src/components/ui/**`    | One implementation per primitive, ever                                  |
| `src/routeTree.gen.ts`    | Generated by `pnpm generate-routes`; never hand-edited, never listed    |
| `src/lib/plans.ts`        | The plan catalogue, browser-safe, no bindings                           |
| `src/lib/money.ts`        | The money primitives; one rounding function in the repository           |

**How a feature plan gets a shared path changed.** It does not. It writes the requirement under its
own **Data and migration**, **UI** or **Quota** heading and stops. That requirement is then minted
here as a stage, in the wave _before_ the requisitioning stage runs. A feature stage whose Owned
paths list names one of the eight is malformed and is rejected before scheduling.

**A wave with no reported requirement mints no stage.** An empty stage is worse than a missing one:
it invites an agent to invent work in the one file where invention is most expensive.

deleted, not filled.

**Which of them closed.** The register above says who holds a concern; this one says whether they
are finished. A stage is **closed** when every reference row it owns reads `→ done`, and **open**
when any row does not. Both columns are re-derivable —
`pnpm exec tsx scripts/plans/audit.ts docs/plans/00-foundations.md` reads the same rows — so neither
is a claim anybody has to take on trust.

`brand_logos` are in `src/server/db/schema.ts`.

Requisitioned by `04-S1` (auth needs the Better Auth tables) and `03-S1` (money needs the
catalogue). No finance-domain table lands here; those are `00-S5` and later.

### Owned paths

- `src/server/db/schema.ts` — new
- `src/server/db/auth-schema.ts` — new
- `src/server/db/ids.ts` — new
- `src/server/db/types.ts` — new
- `src/server/db/__tests__/conventions.test.ts` — new

`enumCheck()` has no file of its own. It is a module-private, unexported function inside
`schema.ts`, which is acceptable because it has exactly one caller — the schema module itself —
and exporting it would invite a second generator of the same `CHECK` clauses. The requirement is
unchanged; the host module is `schema.ts` and is owned above.

### Data and migration

Nothing exists yet; this is the first migration.

- **Conventions docblock** at the top of `schema.ts`, stating verbatim: ids are `text` PKs from
  `newId()` (base36 epoch-ms + `nanoid(16)`, 25 chars, sortable); money is `integer` minor units +
  `text(3)` ISO-4217 with the scale taken from `currencies.digits` and never a hard-coded 2; rates
  are `rate_e10 integer`; calendar dates are `text` `YYYY-MM-DD`, times `HH:MM`, instants epoch-ms
  `integer`; every enum column carries a SQL `CHECK` generated by `enumCheck()` from an exported
  tuple; every FK and every filtered or sorted column has an index; **every tenant table has
  `organization_id` and it is the leading column of every composite index**.
- **Better Auth tables** in `auth-schema.ts`: `user`, `session`, `account`, `verification`,
  `two_factor`, `passkey`, `organization`, `member`, `invitation`. Column **keys stay camelCase in
  TS** (`banReason`, not `ban_reason`) because the `admin` plugin addresses columns by property key
  — this is load-bearing and is stated in a comment at the table.
- **`organization_settings`** (1:1 with `organization`): `base_currency_code text(3) NOT NULL`,
  `locale`, `timezone`, `week_start` (`monday|sunday`), `date_format`, `number_format`,
  `fiscal_month_start_day integer NOT NULL DEFAULT 1`, `hide_zero_balance_accounts boolean NOT NULL
DEFAULT false`, `default_transaction_account_id text NULL`.
- **`user_preferences`**: `locale NULL`, `theme`, `density`, `reduce_motion boolean`,
  `number_pad_on_mobile boolean`.
- **`audit_log`** (tenant, with `organization_id` leading) and **`platform_audit_log`** (global,
  with the four actor-consistency `CHECK`s in declaration order).
- **`currencies`**: `code text(3) PK`, `name`, `digits integer NOT NULL`, `numeric_code`,
  `is_disabled boolean NOT NULL DEFAULT false`.
- **`exchange_rates`**: PK `(base_code, quote_code, date)`, `rate_e10 integer NOT NULL`, `source text`.
- **`brand_logos`**: `domain text PK`, `initials`, `color`, `fetched_at`.
- **`subscriptions`** (Polar mirror, one row per organization) with the columns named in
  `docs/SPEC.md` §5.4, unique on `organization_id` and on `provider_subscription_id`.
- Migration: `pnpm db:generate` produces exactly one new file under `drizzle/`; its name is the
  generator's and is not asserted here. It creates the Better Auth tables, the workspace and user
  settings tables, the two audit logs, the three global catalogue tables and `subscriptions`, and
  it backfills nothing — the database is empty.

### Server (repo, server function, Zod)

None. This stage adds no repository, no server function and no Zod schema; it is a schema module and
its conventions. `src/server/db/types.ts` exports the branded types `Minor = number & { __minor }`
and `RateE10 = number & { __rate }` plus the enum tuples the `CHECK`s are generated from, so that
the repositories minted in wave 1 have something to import.

### UI (route, components)

None. This stage ships no route and no component.

### Quota

This stage creates no runtime row and consumes no metric. The quota metrics themselves live in
`src/lib/plans.ts` and are `00-S4`'s work.

### Tenant isolation test

None yet — there is no repository to isolate. What this stage owes instead is the **precondition**
for every later isolation test: `src/server/db/__tests__/conventions.test.ts` asserts, by reading the
schema module's exported table objects, that (a) every table other than the six named global ones
has an `organizationId` column, and (b) every composite index on such a table lists `organizationId`
first. A table added later without those properties fails this test, not a code review.

### Money invariant

**No amount is written by this stage**, but the representation is fixed here and every later stage
inherits it: an amount is `integer` minor units and a `text(3)` code; a rate is `rate_e10`; there is
no `real`, `float` or `numeric` column anywhere in the money path. The case
`src/server/db/__tests__/conventions.test.ts` → _no floating-point column exists in the schema_
walks every column of every table and fails on any non-integer numeric type. That test is the
mechanical enforcement of `docs/MONEY.md` §1 and no stage may add a tolerance to it.

### Verification

- Command gate: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`.
- `src/server/db/__tests__/conventions.test.ts` holds three invariants: tenant column present,
  `organization_id` leads every composite index, no floating-point numeric column.
- `pnpm db:generate` produces exactly one new file under `drizzle/` and `git diff --exit-code --
drizzle/` is clean afterwards.
- `pnpm db:migrate:local` applies cleanly against an empty local D1, and re-applying is a no-op.
- No browser evidence: this stage renders nothing. No axe run for the same reason.
- Console silent during `pnpm db:migrate:local`.

### Definition of done

The six items of `docs/SPEC.md` §7 apply unchanged. The ten visual clauses of §2 do not apply to
this stage because it ships no surface; that exemption is stated here rather than left to be assumed,
and it is the only kind of exemption this plan set allows — _no surface_, never _no time_.

### Blockers

None.

Neither the queue consumer nor the cron handler is a file. Both are inlined in

The **real, already-provisioned resource ids** are checked in, not placeholders —
`docs/DEPLOY.md` §1–§4 is the authority and this stage transcribes it. `database_id`,
both KV ids per environment, both bucket names and both queue names come from there verbatim. A
placeholder id in this file is a deploy that silently writes to the wrong database.

### Server (repo, server function, Zod)

- `src/server/worker.ts` is the **custom entry** (`"main"`), not
  `@tanstack/react-start/server-entry`, because only the entry module's exports let workerd find the

- `src/server/cron/scheduled.ts` switches on `controller.cron` against **four literal constants**

  plan fills it; a stub that logs is honest, a stub that returns silently is not.
- `src/server/queue/consumer.ts` reads the envelope discriminator and dispatches; unknown kinds

- No Zod at this layer beyond the queue envelope's discriminant parse.

### Quota

No countable row. The **cost model** does change: every binding declared here is a line in

The money suite is four files, not one, split along the module boundaries it covers — the core

### Data and migration

None. `money.ts` reads `currencies.digits` through a value passed to it; it never imports the schema

### Server (repo, server function, Zod)

None — both modules are isomorphic. This is the point: a rounding function that only exists on the
server produces a client that rounds differently, which is exactly the failure `docs/MONEY.md` §8
records.

Exports of `money.ts`: `toMinor(major, digits)`, `toMajor(minor, digits)`,
`roundHalfToEven(value)`, `addMinor`, `subMinor`, `mulRate(minor, rateE10, digits)`,
`formatAmount({ minor, code, digits, locale })`, `parseAmount({ input, code, digits, locale })`, and
the branded constructors `asMinor` / `asRateE10`. Formatting and parsing go through
`@internationalized/number` so the locale's group and decimal separators are the platform's, not a
regex's.

Exports of `plans.ts`: `PLAN_IDS`, `BILLING_INTERVALS`, `ENTITLING_STATUSES`, the metric catalogue
and the module switches of `docs/SPEC.md` §5.4. Polar product ids arrive as **static**
`import.meta.env.VITE_POLAR_PRODUCT_*` references so Vite inlines them; a computed lookup is silently
`undefined` at build.

### UI (route, components)

None.

### Quota

This stage **defines** the metrics but enforces none: `assertWithinLimit` is `22-S1`'s. What it owes
is that the catalogue and the resolver cannot drift — `plans.test.ts` asserts every metric key in the
catalogue is one `resolveLimits()` knows, and the reverse. In wave 0 the resolver does not exist yet,
so the test is written against the exported metric-key tuple and `22-S1` extends it to the resolver.

### Tenant isolation test

None — neither module reads or writes a row. Stated rather than skipped: these are pure functions
over values the caller already holds.

### Money invariant

**This stage is the money invariant.** `money.test.ts` holds, at minimum:

- _rounding is half-to-even_: `2.5 → 2`, `3.5 → 4`, and the negative mirrors.
- _`digits` is honoured, never assumed_: JPY (`digits: 0`) round-trips `¥1234` as `1234` minor, KWD
  (`digits: 3`) round-trips `1.234` as `1234` minor, EUR as `123456` for `1234.56`.
- _no float leaks_: `mulRate` composes integer arithmetic and its result for a known rate matches a
  hand-computed integer, not a tolerance.
- _parse and format are inverse_ for every currency in the catalogue, in both `en` and `pl`.
- _a `pl` group separator round-trips_: `1 234,56 zł` parses to `123456` minor.

### Verification

- Command gate in order.
- The two test files above.
- No browser evidence and no axe run: no surface. The first surface that renders a formatted amount
  is `06-S2`, and it is that stage's evidence that shows the formatting working.

### Definition of done

`docs/SPEC.md` §7 items 1–3 and 5–7. Item 4 does not apply (no surface).

### Blockers

**`OPEN-6`** — whether zero-decimal currencies are in v1 scope. The stage implements `digits`
correctly regardless, because the alternative is a hard-coded 2 that has to be unwound later; what

**`OPEN-1`** — the plan boundary. `plans.ts` cannot ship real numbers for `accounts`, `budgets` and

### Owned paths

- `src/server/db/schema.ts` — edit
- `src/server/db/__tests__/conventions.test.ts` — edit

### Data and migration

Every column is as specified in `docs/SPEC.md` §5 and transcribed here in full in the stage body when
it is written. The properties that must not be lost:

- `organization_currencies` PK `(organization_id, currency_code)` with `is_base boolean` and a
  **partial unique index** enforcing exactly one `is_base` per organization.
- `organization_exchange_rates` PK `(organization_id, base_code, quote_code, effective_from)` with
  `effective_to text NULL` — **ranges, not points**.
- `accounts` carries **no `type` column**. With no connectors every account is manual; the column
  and every branch that would read it do not exist. This is a deliberate simplification and a
  comment at the table says so, so nobody re-adds it as an oversight.
- `transactions.transfer_kind` is `none|internal|external_out|external_in` and answers only _"is
  this a transfer and how many legs"_. Link targets are their own nullable FKs. There is no
  `transfer_nature`.
- `transaction_splits` has a **surrogate `id` PK**, not `(transaction_id, category_id)`, so a receipt
  with two lines in one category is representable.
- `account_balances` PK `(organization_id, account_id, date)` with `native_minor`, `ref_minor` and
  `rate_e10`.
- Migration: `pnpm db:generate` produces exactly one new file under `drizzle/`; its name is the
  generator's and is not asserted here. It creates the per-workspace currency and rate tables, the

## Stage 00-S17 — Schema: the loan tables

### Stage id

`00-S17` · Wave 7 · effort **S**.

### Owned paths

- `src/server/db/schema.ts` — edit

### Data and migration

The full column list, the enums and the four indexes are specified by `28-loans.md` → `28-S1` →
_Data and migration_, and this stage implements that requirement without amending it. Three points
are restated here because they are schema decisions rather than feature ones:

- **`annual_rate_e10` reuses the integer-scaled-by-10^10 convention** of `exchange_rates`. It is not
  an exchange rate and it never resolves through the rate tables — it is scaled that way so this
  schema carries one scaling convention for a fraction and not two (`docs/MONEY.md` §2.1).
- **`loan_instalments` carries `status <> 'paid' or settled_transaction_id is not null`**, the same
  evidence `CHECK` as `recurring_periods`. Both tables answer "was this paid", and a claim without a
  row to point at is how a schedule quietly stops describing reality.
- **`loan_extra_repayments` holds no amount.** It is `(organization_id, loan_id, transaction_id)`
  and a timestamp; the amount lives on the transaction. A second copy of an amount is a second
  ledger.

Enums added: `LOAN_STATUSES`, `LOAN_REPAYMENT_SHAPES` and `LOAN_PAYMENT_FREQUENCIES`, the last one a
narrowing of `RECURRING_FREQUENCIES` to the four that divide a year exactly. It is declared as a
subset of that array rather than a new literal list, so a frequency added to the recurring
vocabulary cannot silently fail to appear here.

Migration: `pnpm db:generate` produces exactly one new file under `drizzle/`; its name is the
generator's and is not asserted here. It creates `loans`, `loan_instalments` and
`loan_extra_repayments` — additive, backfilling nothing. Three new tables and no change to
an existing one, so `docs/DEPLOY.md` §5's non-additive register is unchanged and the previous
Worker's SQL keeps working against the new schema.

### UI (route, components)

No countable row is created by this stage. The `loans` metric that `28-S1` asserts is a catalogue

leading every index, and the repository cases belong to `28-S1`.
