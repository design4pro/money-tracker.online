# 02 — Internationalisation

## Area brief

English is the source locale; Polish ships with it. Two locales, and no third is planned — the
layer is hand-rolled rather than taken from a library (`99-boundaries-and-blockers.md` BND-31),
because with two locales the libraries are all larger than the problem and none of them makes the
parity gate any easier.

The hard requirements: **no user-facing string is hardcoded**, a new key lands in **both** locales in
the same change, Polish's **four plural forms** are handled by CLDR rules rather than an `n === 1`
ternary, and number and date formatting is provably the same in workerd and in every browser engine
we ship against — a divergence is a defect, not a tolerance (`docs/I18N.md`).

Out of scope for translation, and it says so on the page: the long-form legal prose under
`src/routes/legal/**` stays English in v1 (plan `25` owns that statement).

### Data and migration

No new table. Two columns are **read**: `organization_settings.locale` and `user_preferences.locale`,
both declared by `00-S1` and neither yet in the schema — `FND-02` reads `missing → partial` and
defers them to `04-S1` and `24-S1`. Neither is written here either; that is `23-S3`.

### Server (repo, server function, Zod)

- **No repository. One server function, contrary to what this stage assumed.** Negotiation itself is
  a pure function, but the shell cannot call it directly: `src/routes/__root.tsx` is compiled into
  the client bundle too, and `getRequestHeader()` from `@tanstack/react-start/server` has no meaning
  there. So `src/server/fns/locale.ts` wraps it as a `GET` server function the root route's `loader`
  calls — never `beforeLoad`, whose context is not dehydrated into the SSR stream and would re-run
  in a browser that has no request header to read.
- **The first two steps of the chain are not wired, and nothing hides it.** `user_preferences.locale`
  and `organization_settings.locale` reach the seam as optional arguments that nothing passes yet,
  because neither table is in the schema: `00-foundations.md`'s `FND-02` reads `missing → partial`
  for exactly these two and defers them to `04-S1` and `24-S1`. Until then a request's only real
  input is its header. The seam takes the stored values as parameters so the day they exist they are
  passed in and nothing else changes.
- `negotiate(input)` resolves in this order and no other: **user preference → workspace setting →
  `Accept-Language` → `en`**. Every candidate is **normalised against the frozen table, never
  trusted**: an `Accept-Language` of `pl-PL` resolves to `pl`, `pl-x-anything` resolves to `pl`, and
  anything unknown falls through rather than being passed to `Intl` where it would throw at render.
- `locales.ts` is a **frozen table** of `{ code, englishName, nativeName, dir, dateFormat,
numberFormat }`. It does not use `Intl.DisplayNames`: a locale is always named in its own language
  and script, and `Intl.DisplayNames`' output varies by runtime, which would make the language
  switcher's own labels non-deterministic.
- `catalogue.ts` loads catalogues with `import.meta.glob`, **lazily and one per locale** —
  `'./messages/*.ts'`, one chunk per locale, none of them inlined into the entry. The namespace
  split this stage assumed, with the shell namespace eager and a route's messages travelling with
  the route's chunk, did not ship: a request needs exactly one locale, and behind the thunks V8
  evaluates only that one, which is where the startup budget actually goes in a cold isolate. The
  glob pattern has to be a literal for any of that to hold, which is the same requirement that
  rules out ``import(`./messages/${locale}.ts`)``.

### UI (route, components)

- **Route.** None. The provider is mounted by the root route, which is `05-S1`'s file; this stage
  states the requirement and `05-S1` mounts it.
- **Components.** `provider.tsx` wraps RAC's `I18nProvider` — that single wrapper is what makes

  cites i18n as a React Aria benefit rather than a cost.
- **States.** Not applicable — no async surface.
- **Tokens.** None.
- **Accessibility.** `<html lang>` and `dir` are set from the negotiated locale on the server, in the
  first paint. Both locales are LTR, so `dir` is a correctness detail rather than a layout one, and
  the code sets it anyway rather than hard-coding `ltr`.

### Tenant isolation test

### Money invariant

Formatting a **currency** is `src/lib/money.ts`, not this layer. The rule is unchanged — an amount
enters a message already formatted by `formatAmount`, with its locale and `digits` applied, or it
does not enter one at all, which is what keeps `1,234.56` out of a Polish sentence.

**The guard this stage claimed for it does not exist.** `catalogue.test.ts` was said to assert that
no message file contains a currency symbol, a hard-coded decimal separator or a `{amount}`
placeholder interpolated as a raw number. It asserts none of those: its thirteen cases cover the
loader's laziness and caching, the translator and the stored-key renderer, and `currency` appears
nowhere in `src/lib/i18n/__tests__/` outside a comment in `interpolate.test.ts`. `parity.test.ts`
does not carry it either. What holds the money-adjacent line today is `02-S2`'s placeholder parity —
every key keeps the placeholder set English gave it, money-bearing keys included — and the design of
`interpolate.ts`, which substitutes with `String()` and never with `Intl`, so a raw `{amount}` renders
as a bare integer rather than as a plausible-looking wrong figure.

Writing the missing assertion is real work and is tracked on #108 rather than claimed here. A plan
that says a money guard is in place is how the guard stops being written.

### Verification

- Command gate.
- `negotiate.test.ts`: the four-step order, `pl-PL → pl`, an unknown tag falling through to `en`, a
  malformed `Accept-Language` not throwing, and a user preference beating a workspace setting.
- `catalogue.test.ts`: loading a locale evaluates that locale's file and no other, once however
  many times it is asked for and once across concurrent requests; a locale with no file renders
  keys rather than throwing; both shipped catalogues load. The currency-symbol case this bullet
  used to promise was never written — see **Money invariant**.
- No browser evidence of its own: the first localised surface is `04-S4`'s auth screens, and those
  frames are the visual evidence. Stated rather than omitted.
- No axe run for the same reason.

§7 items 1–3 and 5–7. Item 4 does not apply (no surface).

## Stage 02-S2 — Polish plurals, the message format and the parity gate

### Stage id

`02-S2` · Wave 1 · effort **M**. The stage that makes "EN + PL parity" a test rather than a promise.

### Reference rows

`I18N-04 missing → done` — `src/lib/i18n/plural.ts`, checked by
`src/lib/i18n/__tests__/plural.test.ts`. The four categories are **transcribed**, not asked of
`Intl.PluralRules` at runtime; **Server** below records why that reversed this stage's design.
`I18N-05 missing → done` — the interpolation contract shipped as `src/lib/i18n/interpolate.ts`, a
module of its own rather than part of `src/lib/i18n/format.ts`, and it returns a string rather than

`src/lib/i18n/__tests__/shipped-plurals.test.ts` was added beside it for the thing parity can count
but cannot read: whether a Polish branch that exists actually says something different.

### Data and migration

None.

### Server (repo, server function, Zod)

- `plural.ts` exposes the **category set per locale**: English has `one | other`; **Polish has
  `one | few | many | other`** and all four are required in a Polish plural message. A message
  declaring three forms is a test failure, not a fallback.
- **It transcribes the two CLDR rules rather than wrapping `Intl.PluralRules`, which is the reverse
  of what this stage specified.** `Intl` answers the same question correctly in every runtime we
  deploy to, but it answers it out of whatever CLDR release the engine bundles, and workerd, Node,
  WebKit and Chromium do not ship the same one. Plural selection decides which of four Polish
  sentences renders, so a category that differs between the server pass and hydration is a
  text-node mismatch on every counted noun on the page — the failure `02-S3` was meant to make
  visible and, unshipped, did not. `plural.test.ts` still cross-checks every category against
  `Intl.PluralRules` over 0…1200, so a CLDR change that genuinely moves Polish is a red test rather
  than silence.
- `interpolate.ts` performs interpolation with a fixed placeholder syntax and **no runtime eval**.
  Values are escaped by React, not by the formatter. **It returns a string, not parts**, so the
  `<strong>`-inside-a-message case this stage described is not supported: the syntax is `{name}` and
  nothing else, and a sentence needing markup is split or passed an already-formatted string. A
  message layer that grows a grammar grows a parser, and this one deliberately did not.
- Auth-screen schemas are a **factory** taking `{ t, locale }` (`04-S4`), because Zod bakes its
  messages at construction and the auth screens run before any stored preference exists. That
  requirement is stated here so `04-S4` does not discover it at implementation time.

### UI (route, components)

- **Route.** None.
- **Components.** None.
- **States.** Not applicable.
- **Tokens.** None.
- **Accessibility.** Polish's four plural forms are an accessibility concern as much as a
  correctness one: a screen reader announcing _"3 transakcja"_ is wrong in a way that costs a
  listener more than it costs a reader. The plural test is the guard.

### Quota

No countable row.

### Tenant isolation test

None — no data access.

### Money invariant

`parity.test.ts` carries the money-adjacent case: **every message key that names an amount, a rate or
a currency exists in both locales with the same placeholder set**. A Polish message that drops the
`{currency}` placeholder renders a number with no unit, which in a finance product is not a cosmetic
bug. Named case: _money-bearing keys have identical placeholder sets across locales_.

### Verification

- Command gate.
- `parity.test.ts` is the completeness gate: **the EN and PL key sets are identical**, every key's
  placeholder set matches, and no key's value is the empty string. It runs in `pnpm test`, so a PR
  adding an English key without its Polish sibling fails CI rather than shipping an English string
  into a Polish page.
- `plural.test.ts`: Polish `1 / 2 / 5 / 22 / 25 / 1.5` map to `one / few / many / few / many / other`
  and each has a distinct rendered form; English `1 / 0 / 2` map to `one / other / other`.
- No browser evidence of its own; the localised surfaces are verified by their owning stages, each of
  which captures both locales.
- No axe run: no surface.

§7 items 1–3 and 5–7. Item 4 does not apply (no surface).

### Money invariant

The fixture's cases are dominated by money, because that is where divergence hurts: **EUR, PLN, JPY,
KWD and USD**, each at a boundary value (zero, one minor unit, a thousands boundary, a negative), in
both locales. If workerd's `Intl` and WebKit's disagree on a group separator for `pl` + PLN, this
test says so instead of a user noticing. Named case: _server and browser format every money fixture
identically_; a divergence is **frozen into a lookup table and recorded in `docs/I18N.md`**, never
absorbed as a tolerance.

### Verification

- Command gate.
- `runtime-parity.test.ts` runs the fixtures under the Node/workerd test environment and snapshots
  the output.
- `e2e/i18n-parity.spec.ts` runs in both browser projects (`chromium`, `mobile-safari`), fetches the
  server rendering and asserts string equality per case. **A failure names the case, the locale, the
  currency and both strings** — a diff that says "expected 1 234,56 zł" and nothing else is not
  actionable.
- No visual frames: the spec asserts strings, and a screenshot of a string is weaker evidence than
  the string.
- No axe run: no surface.

### Definition of done

§7 items 1–3 and 5–7. Item 4 does not apply (no surface).

### Blockers

**None, and that is the point: this stage was never blocked, it was skipped.** The risk it was
written to retire is now a defect in the tracker rather than a hypothesis in a plan — issue #163,
_Polish date ranges hydrate differently on WebKit_, is `formatCalendarDateRange(locale, start, end,
'medium')` rendering `1–31 sie 2026` on the server and `01–31.08.2026` in WebKit, failing the
console gate on every Polish page that shows a budget period. That is exactly the case
`format-cases.json` was to enumerate and `e2e/i18n-parity.spec.ts` to assert — one stage earlier,
and against a fixture instead of against a reader.

Two decisions made elsewhere in this plan lean on the missing test and should be read with it:
`plural.ts` transcribes its CLDR rules rather than asking `Intl` (`02-S2`), and
`src/lib/i18n/__tests__/source-rules.test.ts` bans `Intl.DisplayNames` outright (`02-S1`). Both are
this same divergence, worked around one API at a time because no gate exists that would catch the
next one.
